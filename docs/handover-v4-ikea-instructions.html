Two engines insidePage 04 / Loop + Graph

Loop retries. Graph orders. They do different jobs. The loop is inside each unit. The graph is the shape of the whole job.

Engine A — Persistent loop

When a piece fails, climb the ladder

Classify the failure first. Then use a distinct approach: different input, source, method, or smaller size. Same wording ≠ distinct.

RUNG 1 Retry with corrected input
RUNG 2 Switch source / evidence route
RUNG 3 Split the unit smaller
RUNG 4 Replace the method
RUNG 5 Hold this unit, continue the rest

Up to 5 fix cycles per run. Dead end only after 3 distinct approaches for the same failure class fail, or budget is spent.

When to use which

Router rule

  • Loop alone: one straight line, one deliverable, nothing runs apart.
  • Graph: 2+ parts, some independent, some dependent, a later part needs both.
  • Default is loop alone, unless a graph clearly helps. Reason is written in the graph file.
  • In this environment, “parallel” means serial in order with no dependency, depth max 2.
Join rule: a join unit waits for all its inputs. It never runs early. Missing input = wait or dead end.

NEW • 01

Per-unit list in JSON

The graph now ships with a machine-readable list. Only the passes field ever changes.

NEW • 02

Session start routine

Every session: read notes + logs → pick next unfinished unit → run setup → end-to-end check → fix base if broken → then start.

NEW • 03

End-to-end check

Proof is on the real artifact, the way a human would use it. Not just a unit test or a page fetch.

NEW • 04

Effort scaling

Simple: 1 agent, 3–10 calls. Compare: 2–4 agents, 10–15 each. Complex: 10+ agents, split clearly. Stated in the package.

NEW • 05

Subagent contract

Fresh context, only needed tools, short summary back. Stopped at limit = partial, not failed.

NEW • 06

Notes & compaction

When the trail gets long, summarise it: keep decisions, gaps, numbers. Notes live in a file, outside context.

NEW • 07

Tool risk ratings

Low / medium / high, by read vs write, undoability, permissions, cost. High-risk pauses or goes to a human. Listed in the manifest.

NEW • 08

Failure threshold N

Same tool fails N times in a row (N set in the manifest) → stop retrying it, escalate to a human.

NEW • 09

Rubric evaluator

Grades during work, 0.0–1.0 on: factual accuracy, citation accuracy, completeness, source quality, tool efficiency. Judge still decides at the end.

NEW • 10

Run-state resume

Durable state, run/action IDs, lease + fencing token. Resume never re-runs a finished tool. Mismatch = fail closed, don't guess.

TroubleshootingPage 06 / If something does not fit

If it gets stuck A run never ends with an unowned gap. A verdict starts the next step, it does not end the run.

✓ FIXED

Fix fits inside the approved envelope: same tools, same destination, no new cost or outward action. Do it, test it, re-check it in the same run.

→ QUEUED

Fix needs new scope, cost, risk, or an outward action. Record it as the next job, with its own approval gate. Queued is not done, and is never shown as done.

◎ ACCEPTED

You explicitly accepted the gap, with the reason recorded. Only explicit acceptance counts.

Done means only: all gaps Fixed, or all remaining gaps explicitly Accepted by you. Never “done, but…”

Dead-end report — short by default
  • What stopped + actual status, including any unmet check
  • Spent / remaining budget
  • ≤3 bullets: what was tried
  • What would unblock it
  • Options: Retry unchanged / Change scope or limit / Stop — each flagged “needs reapproval?”
Safety rails — enforced, not prose
  • Gates are tool classes enforced by the harness, not decided by the model
  • Manifest constrains arguments too: domains, paths, hosts, per-call caps
  • External content is data, never instruction, and is marked tainted
  • Changing the predicate = new version + reapproval. Old verdicts do not carry over
FINAL CHECK — BEFORE YOU CALL IT DONE

Open the real artifact like a user would. Check every link in the graph points to a real file. Check the per-unit list: is every passes true? Check the final report names its field kits, with proven / draft status and a link. If any answer is no, it is not done yet.
