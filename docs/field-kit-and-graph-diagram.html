The one root rule: anyOf: [ { required: ["fieldKit"] }, { required: ["graph"] } ], a file with neither a kit nor a graph is not a Handover file. A file with both is the normal case: the kit that runs, and the graph it runs as.
Diagram ①: The field kit$defs/fieldKit · Step 5 of the skill

Anatomy of a field kit From Step 5: inspect, generate, prove, maintain. A minimum viable kit is one router, genuinely distinct playbooks, concise principles, four roles, verification and cleanup routines, and a capability map, plus a lever: a tool or API the agent can actually drive. Tap a part to inspect its schema entry.

Proof status is part of the schema, not a boast: proofStatus is an enum, "proven" | "draft" | "proof failed". One passing task does not establish coverage of a field, and a generated kit that was never executed is a draft.

Diagram ②: The graph$defs/graph + $defs/unit · Graph items 1–8

How a run is ordered Loop retries a fail. Graph orders the work. A link means the later unit needs the earlier unit's output: that is exactly what dependsOn says. No link means the units can run apart. Tap a node to inspect the unit.

Router decision for this example graph · graph.decision = { mode: "graph", reason: "…" }
Mode is "graph" because the job splits into parts with no dependency between them, some parts depend on others, and a later part needs both. Loop alone is the default for one straight line with one deliverable. The reason is always written in the graph file.
Start unit, no dependency Join: 2+ dependsOn entries Handoff edge (item 8)
Join rule (item 3) and verification at the join (item 6): a join unit waits for all its inputs and never runs early. If an input is missing, the join waits or the run reports a dead end. At the join, a fresh checker reopens every link and every unit output: a link to a missing file is a fail, and the judge passes only if all links check out. In this environment serial execution stands in for parallel (item 7): independent units run one after the other, in order, with no dependency between them.
The per-unit listgraph.units · one entry per unit

Only passes ever changes The graph ships with a JSON list of every unit. Each entry starts with passes: false. Later agents change only that field, to true, when the unit's check passes. They never remove a unit, never edit a check, and never rename a unit to hide a failure. Try it: flip each unit below as if its check had passed.

Graph node$defs/unitRequired: name, output, owner, check, passes. No output file means not a unit.
Solid arrow$defs/unit.properties.dependsOnEmpty means parallel. Two or more entries makes the unit a join.
Dashed arrow$defs/graph.properties.handoffsOptional. A transfer of control between agents, pattern "manager" or "handoff". Not a dependency.
