## What Handover is, in plain words
You write a rough prompt. Handover proposes an interpreted intent and plan, marks its assumptions, and asks only the questions that would change that plan. You approve or reject the whole package. If you approve, Handover builds or picks a field kit for that kind of work, then runs the work without you babysitting it, and reports back with proof, or with a clear dead end if it cannot finish inside the limits you approved.

Handover is distinct from pstack's Babysit playbook. That playbook gets a pull request to merge-ready. Handover gets a rough prompt to an approved, running job.

## The five inputs, used as a checklist, not five questions
The five inputs are coverage to check, not questions to ask every time. Infer an answer from the prompt and context, or propose one, and ask the human only where a missing answer would change the plan, the acceptance check, or the authority.

1. Outcome: what decision or deliverable this should serve, and for whom.
2. Proof on the real artifact: what observable result would make you accept it. Propose a concrete check for approval where possible.
3. What must not change: constraints and existing assets that are non-negotiable.
4. One-way doors: actions that pause for a human. Default gates: publish, send, pay, delete, deploy, and any other external commitment.
5. Stop condition: attempt, time, or cost limit, plus a dead-end report if the finish predicate is still unmet. Exhaustion is a dead end, never a weaker success claim. A plateau is not completion, and the predicate is never relaxed to declare victory.

A question is human-only when it is about preference, authority, risk acceptance, a non-negotiable constraint, or a tradeoff with no authorized rule. Everything else, the agent should settle by reading, inspecting, or experimenting, and record the result and where it came from. If investigation exposes a new consequential choice outside the approved envelope, it pauses instead of inventing consent.

## How Handover talks to you: options first, short by default

This is a design rule, tested in v1, not a style preference.

Every question Handover asks comes with suggested options. Never ask an open question with no options, unless the user explicitly asked for an open-ended question.

Each question follows the same shape:
- One short plain sentence stating the decision, in plain words, no jargon.
- Two to four options. Each option is a name plus its tradeoff in 12 words or fewer, for example: "Faster, less proof" or "Slower, checked on the real artifact."
- One option marked as recommended, with one line saying why, in plain words.
- One escape option: "Something else, in my words." The user can always type a different answer.
- One guided option for when the user does not know: "You decide within the limits I approved." This option is available only after an envelope exists, and only for a choice already inside that human-approved envelope. It is never available for: Stage 1 or Stage 2 approval itself, the predicate, the budget cap, the tool allowlist, a one-way door, an amendment, or a new risk. Before any envelope exists, in the translator stage, "You decide" is unavailable. Instead, Handover presents a proposed choice for explicit inclusion in the Stage 1 approval package, so the human approves it, not the agent by default. Who decides whether a choice is inside the envelope is the harness, by checking it against the approved manifest, never the model that proposes it. Every delegated choice made after approval is listed in the record as "Handover chose X." Tapping "You decide" never counts as approval of a gated action; a gated action always needs its own separate approval, bound to the exact action and payload.

Options must be real. Each option must change the plan, the cost, the scope, the proof, or the risk, and the translator must say which one it changes. A list of options that all lead to the same plan is not options, it is decoration. Translator labels are proposals only. The harness structural diff is the authoritative classification of a change, and if a label and the diff disagree, the diff wins and reapproval is required.

One decision per message, in the order that changes the plan most first. Related questions are bundled only when a single tap answers them, for example by picking a preset package. Otherwise, split them. This replaces the earlier bundle-related-questions advice where it conflicts with low load.

Short by default, details on demand:
- A normal interaction is a headline first, then options, in about 120 words as a target for the first screen, not a ceiling on information needed for consequential consent, unless the user asked for detail.
- The approval package is shown as a short summary first, followed by a compact approval card that is always visible, not only on demand, containing the material terms: outcome, check that proves it, verification coverage and permissible claim, what will not change, cost and limit with hard versus advisory stated, verification reserve, Case B generation and proof budget where it applies, exclusions, gates, autonomous actions with their tools and destinations, prohibitions, relevant assumptions, and the applicable package and manifest version identifiers, plus the Stage 1 passing and failing predicate examples. Stage 2 needs a comprehensible description of what its manifest authorizes, not just a version number. The comprehension test must include recall of tools and destinations and of action payloads, as well as proof and limits. Then approve or reject, then "Show full package" for the complete version. Stage 1 and Stage 2 approvals are separate surfaces, each bound to its displayed package or manifest version. If a decision cannot be understood concisely, use additional short screens before the approval action, never hide a material term behind "Show details.
- Progress reports use the short board style Richardson prefers: Planned, In progress, Done recently, with short checklist lines, sent fresh when status changes, not a dense report.
- A stuck or dead-end report is short: what stopped, the actual status including any unmet predicate or coverage gap, spent and remaining budget, at most three bullets on what was tried, what would unblock it, and options such as Retry unchanged, Change scope or limit, or Stop. Each option is flagged as needing reapproval or not, so a retry that narrows scope or changes a limit is shown as an amendment, not a routine retry: it requires a new predicate version and reapproval, and exhaustion remains a dead end. A progress board must never imply completion while verification is inconclusive.
- If a decision genuinely needs more explanation, offer "Explain in plain words" as an option instead of putting a dozen paragraphs in the main message. The user pulls detail when they want it, Handover never pushes it.

Enjoyable means easy, not chatty. Warm and plain, no slogans, no formulaic sentences, no em dashes, no jargon without a plain explanation in the same line. A small win is stated plainly, for example "First unit verified," not celebrated with a paragraph.

Where this rule applies: translator questions, the approval gate, one-way-door gates, stuck escalations, and kit proof reports. Where it does not apply: internal agent-to-agent messages, the decision trail (which stays terse but complete), and verifier evidence (which is a record, not a user interaction). A short user message never means a short evidence record.

V1 release blocker for this rule: test comprehension and accurate consent, not tapping alone. Test cases must include: a user who does not know the answer and finishes by tapping options, a rejection, a delegation boundary case where "You decide" is correctly unavailable, both Stage 1 and Stage 2 approvals, and a dead-end or gated action. The test passes when the user can state back, in plain words, what was approved, what will be checked, and what limit applies, without reading the full package.

## Two-stage approval, fixing the v0.1 contradiction
V0.1 said the human approves a selected kit, while also saying the kit is built after approval. That cannot both be true. V0.2 splits approval:

Stage 1, approve the intent package: intent and audience, deliverable, finish predicate, constraints and assumptions, authority envelope, plan outline, verification approach, iteration and stopping rules, operations, and budgets. The package must state one of two kit cases, with no third case:
- Case A, existing proven kit: the package names the kit and its version digest.
- Case B, kit to be generated: the package states that plainly, with a separate budget line for generation and proof, and declares that the first real task is the proof run. Failing that run produces a partial-proof report, not a second attempt on the user's budget.

Stage 2, approve the versioned execution manifest, required before unattended execution: kit and playbook digests, tools and targets allowlist, predicate version, limits, and budget ledger. The manifest is what the human authorized to run, not the prose package alone. Generated instructions are treated as untrusted until validated against the manifest.

Repairs are classified by the harness, never by the model that proposes them. The harness computes a structural diff between the proposed execution state and the approved manifest over an enumerated field list: tool set and argument scopes, external targets, predicate hash, budget figures, playbook and kit digests, and steps marked as method-bearing at Stage 2. Any non-empty diff on those fields forces reapproval. Only an empty diff lets the repair proceed. Every repair is logged with its diff, so near misses can be audited. Defining consequential method as that enumerated list removes the judgment call entirely. For the pilot, execution is a closed, versioned bundle covering executable instructions, scripts, configuration, and tool scopes. Untracked execution changes are denied or require reapproval, and adversarial mutation tests must show that a consequential change to an unmarked script or configuration cannot pass as an empty diff. Runtime sandbox enforcement stays independent of the diff, so a diff failure and a sandbox failure are separate checks. The initial package approval is separate from later one-way-door action approvals, and each action approval is bound to the exact action and payload, so a modified payload after approval is a new approval, not a reuse of the old one.

Predicate amendment path: a human may amend a predicate, but the amendment creates a new predicate version, requires reapproval, and invalidates verdicts tied to the old version. Verdicts are never carried over across a predicate change.

## The approval package, contents
One complete package, with assumptions marked, containing:

1. Intent and audience: desired outcome, recipient, intended use.
2. Deliverable: exact artifact, format, location, and supporting materials.
3. Finish predicate: independently observable checks on that artifact, fixed at approval, including verification coverage (see below).
4. Constraints and assumptions: what must not change, domain boundaries, assumptions the agent may act on.
5. Authority envelope: autonomous scope, methods, time and cost, explicit one-way-door gates, prohibited actions, and the tool and target allowlist.
6. Plan and routing: selected playbook and field kit (or kit-to-be-generated, Case B), stages, ownership, dependencies, justified parallel work, and the v1 depth and spawn limits.
7. Verification: deterministic checks first where available; generator and verifier separated; verifier gets the specification and the artifact or evidence, never the generator's persuasive work history; judge resolves verdicts and records gaps, and cannot convert a gap into a pass.
8. Iteration and stopping: stuck ladder, alternative routes, maximum attempts or budget, dead-end report.
9. Operations: checkpoint and resume state, scheduler or parent re-invocation if needed, artifact and version tracking, decision trail, cleanup, and the budget ledger.
10. Approval: approve or reject the whole package, including proposed assumptions and limits.

The approval gate itself follows the options-first rule: summary first, full package on demand, approve or reject as options, plus "Show full package" and "Something else". Approval authorizes execution inside that envelope only. The agent does not return with routine research questions, and does not ask the user to perform verification. It still pauses at a predeclared one-way door, a missing permission, or an unavoidable conflict outside the envelope. No babysitting is an operating objective, not a promise that inaccessible resources or external approvals can be bypassed.

## Enforceable gates, not prose gates
V0.1 listed one-way-door verbs and left the model to decide whether an action counted. V0.2 requires gates to be tool-call classes enforced by the harness: an allowlist of tools and targets per envelope, with everything else denied or routed to the approval queue. The model never decides at runtime whether something counts as a one-way door.

The manifest must classify the ambiguous cases in advance, for example: a read-only search API call is not a send, writing to a shared document is a publish, overwriting a draft is a delete. Argument constraints are part of the manifest, not just tool names: recipient domains, path prefixes, repositories, URL hosts, per-call spend caps, and maximum record counts. The harness rejects calls outside those constraints before execution. Values originating from external content are marked as tainted; any consequential action whose arguments carry taint and are not on the manifest's declared target list escalates to a human gate. For the pilot, network and filesystem operations are mediated through a sandbox, including redirects and resolved paths, and data and destination rules apply to payloads, so a permitted search call cannot leak private document text in its query. External content is data, never instruction: a retrieved page, file, or message cannot add a tool, a destination, or a permission. The v1 blocker tests are a simulated gated action test and an injection test where external content attempts to redirect an allowed tool; both must block or escalate in every case, tested before live data is used.

## Execution, borrowed from pstack and from delegated verification
- Router, not worker: a coordinator owns the plan, the execution record, and every spawn. The execution record identifies the approved playbook version and records each instantiated step, deviation, and reason.
- Separation of powers: author is never verifier. A verdict is tied to a digest of the artifact and its evidence manifest, and re-checked after any change that affects claims, citations, or sources. Rebinding a verdict to a new artifact version requires a new verification pass.
- Decision trail: one append-only log, one line per decision, with a pointer to evidence, never a paragraph. A checker compares the decision log with the available event record at the end of a run, and reports missing or unverifiable entries, with the events captured and retained stated in the manifest.
- Verification coverage, stated in the predicate: for non-code fields, the predicate must say the population, the selection method, the coverage result, and the permissible claim, plus what counts as inaccessible evidence, and the pass, fail, and inconclusive rules. A verifier sampling 5 convenient citations of 100 cannot report the whole predicate passed. Source content is treated as hostile data, claim-to-source links are independently checked, and the verifier and judge are tested with biased samples, fabricated evidence, and injected instructions. Test verification with known-bad artifacts, not only with successful runs, and state the pass threshold in the manifest for the pilot; the default is that every known-bad case in the test set must be rejected. A digest proves which bytes were checked, not that the check was sound. The judge runs in a fresh context with access only to the artifact, the predicate version, and the evidence, never to the producer's reasoning or self-assessment. At Stage 1, the approver is shown at least one passing example and one failing example the predicate would produce, so they approve behavior rather than prose.
- Fan-out discipline: start with one unit end to end before fanning out. Judge stalled workers by side effects such as pushes and artifacts, not by status text. After two retries for the same cause, drop the unit, record a gap, and replan. A gap does not count as a pass.
- Stuck ladder: try the next route, change the method, or make an operational retry that leaves the approved deliverable and predicate unchanged, then report a dead end with what was tried and what would unblock it. Narrowing the scope or changing a limit is not an operational retry, it is an amendment, and it requires a new predicate version and reapproval. A duration is not a finish condition.
- Pause and resume, with a failure protocol: stop only at a safe boundary, make work durable, write a resume note that an agent with no prior context can use. Resume reuses only work whose completion and artifact version are durably recorded and verified. The run uses a durable state machine with run and action IDs, an action ledger, and duplicate-run protection such as a lease with a fencing token, so a stalled worker that wakes after lease expiry cannot write. For tools without idempotency keys, the manifest defines a reconciliation procedure per tool. Where a tool supports it, use idempotency keys. For an external action with an uncertain outcome, reconcile against the destination or pause for human review, never blindly retry. Do not redo completed work that is durably verified, and do not assume an unrecorded action did not happen.
- Learning loop: reflect and correct. A mistake class counts once it has happened twice. Fix it at the highest level that works, in order: architecture, types or structure, lint or script check, test, docs last. Nothing learned changes a kit until the human approves, except where a prior envelope explicitly authorizes it. Automatic learning-loop changes are cut from v1.
- Cleanup: kill only what the run started, never the evidence. A generated kit that was never executed is a draft, not a deliverable.

## Budget ledger, replacing the v0.1 fan-out numbers
V0.1 said about 10 workers per coordinator and max 3 levels, which permits roughly 1,000 workers, and about 3,000 spawns with retries, with no shared cost control. V0.2 replaces that with:

- One budget ledger owned by the root coordinator, with its unit stated in the manifest, dollars primary, plus tokens or wall time where those are metered. Every spawn is a budget reservation, refused when it would exceed the remaining amount. Estimated spend for model calls and paid tools is also reserved, not only spawns, actual charges are reconciled against reservations, and unused reservations are refunded to the ledger. Where the platform cannot block further calls at the limit, the run uses a capped account or small prepaid allowance and requires human approval before costly steps.
- A reserve held back for verification and the dead-end report, at least 15 percent, sized to the verification estimate in the manifest, so a run cannot spend its verification budget on generation and a large artifact does not leave verification underfunded.
- V1 limits: depth max 2, a hard spawn count stated in the envelope, and serial execution by default. Parallelism is added only after measured tests against actual Muse limits, not from the draft's numbers. Elapsed time limits must state whether approval waits count.
- If hard spend enforcement is unavailable in Muse, the limit is labelled advisory in the manifest, and the deployment boundary is made safer, for example by a smaller scope or a human gate before expensive steps. An advisory limit is never presented as a hard control.

## Field kit generator: inspect, generate, prove, maintain
This is the pstack-like engine for any field, generalized beyond code.

1. Inspect: read the task, available materials, domain standards, tools, and environment. Identify the artifact, the recipient, failure modes, permitted actions, and independently checkable evidence. Ask the user only for unresolved human decisions from the five inputs above.
2. Generate: create a project-local kit with a router, task playbooks, domain principles, role definitions, verification and cleanup routines, and a capability map. Every kit needs a lever, not just prose: a tool or API the agent can actually drive, plus a map of the domain it operates on, in the same way a code kit needs a CLI plus a feature map. Remap roles to Muse models and tools that actually exist, never to Cursor model slugs or paths.
3. Prove: run the kit on one real, authorized task. Check the resulting artifact independently against the agreed predicate. Repair is allowed before the first proof verdict only for fields with an empty harness diff, as defined in the two-stage approval section. If it cannot pass, hand over a failed or partial proof, not a claim that the kit works, and a second real-task proof requires separate approval and funding. One passing task does not establish coverage of a field.
4. Maintain: record decisions and failures, correct a recurring mistake class at the highest effective level, and revalidate after meaningful changes to the kit, sources, tools, or artifact.

Minimum viable kit, before any claim of operational: one router, a few genuinely distinct playbooks for the field, concise principles, coordinator, generator, verifier, and judge roles, evidence and verdict templates, a stuck and resume ladder, cleanup, and a capability map. Add dozens of workflows only as distinct, tested task patterns justify them, not as generated inventory.

Research example:
- Real artifact: a research brief or evidence synthesis the recipient can use, with claims, qualifications, citations, and a reference and evidence ledger, not search logs.
- Drive: execute a defined research question, search specified sources, screen against inclusion criteria, extract findings, synthesize, produce the brief, on a real question.
- Evidence: accessible source records or permitted snapshots, search queries and dates, inclusion and exclusion decisions, claim-to-source links, and checks for source quality, recency, contradictions, and retractions where relevant. A verifier samples or checks links and claims against the underlying sources, at the coverage stated in the predicate.
- Feature-map analogue: a research capability map connecting question types, such as comparison, landscape review, or fact check, to search routes, source requirements, synthesis methods, checks, and known limits.

Three generator failure modes, and the check that catches each:
- Generic kit with field labels, plausible instructions but no field-specific execution or proof. Tested by a real-task proof that requires the capability map, playbook, and verifier to demonstrate field-specific steps and evidence, with the field-specific steps and evidence exercised recorded. A single passing task may expose a generic kit; it cannot establish that the kit is not generic across other tasks.
- Circular verification, where the verifier trusts the generator's summary or citations. Tested by giving the verifier only the spec and the artifact or evidence, and requiring source-to-claim checks at the stated coverage, with inaccessible or contradictory sources recorded as gaps.
- False completion or unsafe autonomy, where the kit declares success on partial work, weakens the predicate, or crosses an authority boundary. Tested by a judge checking the artifact-bound verdict against the original predicate and decision trail, plus a test of budget exhaustion and a simulated gated action before unattended use, and by testing whether the judge rejects a verdict with known predicate violations, missing evidence, or an unauthorized action. A judge decision alone does not prove enforcement without complete, trustworthy event capture.

## Muse translation gaps, release blockers before unattended use
- Overnight and autopilot loops: Cursor /loop has no direct Muse equivalent. Do not promise overnight operation until a scheduler or parent re-invocation path, with duplicate-run detection and failure reporting, has been demonstrated end to end, including resume after a process restart, and fault injection at every side-effect boundary.
- Drive layer: Muse needs its own drive layer or an explicit gap note per field, since pstack's control surface does not transfer.
- Skill paths and frontmatter: user skills live under ~/workspace/custom-skills/, generated kits live project-local. Test a real generated skill through the actual Muse loader, including invalid frontmatter, name collisions, precedence against user skills, reload behavior, and a restart, before calling a generated kit operational.
- Model roles: remap by role and family diversity, never by Cursor slug. Test whether a verifier from a different model family is available in Muse, and what happens when it is not. Family diversity is deferred until availability and its effect on verification are tested.
- Approval surfaces: identify where a human sees and authenticates both the package and later gated actions, and test rejection, expiry, replay, payload modification after approval, and an unavailable approver.
- Subagent limits: establish supported spawn APIs, nesting, concurrency, cancellation, timeout, context and artifact access, and test saturation, child failure, orphan cleanup, and retry limits.

## Build priority, revised by review round 1
1. First: one narrow, supervised workflow for a single artifact type, with a versioned approval manifest, enforceable tool permissions, explicit action gates, artifact-bound verification, and dead-end reporting. Exit criterion to move to stage 2: the simulated gated action test and the injection test both pass in every case, every known-bad artifact in the test set is rejected, and one supervised real run completes with a clean audit of its decision trail and budget ledger.
2. Next: durable execution, with checkpoints, action ledger, restart reconciliation, duplicate-run protection, and shared budget enforcement. Fault-inject crashes and concurrent invocations before enabling unattended runs.
3. Then: Muse integration proof, covering skill loading, approval surfaces, scheduler invocation, metering, and limited subagent use in the target environment, starting serial.
4. Defer: general field-kit generation and automatic maintenance until a hand-built kit succeeds and fails transparently on multiple representative tasks. Defer model-family diversity until tested.
5. Cut from v1: arbitrary-field support, three-level fan-out, automatic learning-loop changes, and claims of overnight autonomy. Research is a possible pilot, not evidence that the generator works for any field.

## What this draft deliberately does not copy from pstack
Cursor commands, paths, model slugs, and loop assumptions; software-specific checks as universal checks; exact skill counts or playbooks just to match pstack; a todo list as a substitute for demonstrated execution; and never-block-on-the-human as a default. Handover's approve and reject gate is a deliberate deviation from pstack's default, and it is stated here as such.
